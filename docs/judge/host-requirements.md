# YCA-400 (#157): хост-окружение для песочницы judge

Отчёт по спайку. Определяет, **на чём** мы строим песочницу нашей тестирующей системы
и **что требуется от хоста**. Спайк кодом не закрывается — результат это решение,
требования и процедура проверки (`scripts/judge/host-probe.sh`).

Статус: решение принято, **проверка на проде — за нами** (см. раздел 6).

---

## 1. Решение (TL;DR)

- Песочница строится на **isolate** (`github.com/ioi/isolate`), не на nsjail.
- Judge — **отдельный микросервис** в своём контейнере; привилегии для песочницы
  выдаются ТОЛЬКО этому контейнеру, backend остаётся без них.
- Хосту требуется **cgroup v2 (unified)** и современное ядро. Контейнеру judge —
  повышенные привилегии и доступ к cgroup-дереву.
- Swap на судейском хосте должен быть **выключен**, CPU governor — `performance`.

---

## 2. Почему isolate, а не nsjail

Оба умеют изоляцию (namespaces, ограничение ресурсов). Разница в том, **подо что они
спроектированы**.

**isolate** написан для судейства олимпиад (используется на IOI и в CMS). Из коробки даёт
ровно то, что нужно для честного вердикта:

- раздельные лимиты **CPU-времени** и **wall-времени** (+ «extra time» — защита от
  случайных выбросов на нагруженной машине);
- лимит памяти через **cgroup memory** — считается реально потреблённая память,
  а не размер адресного пространства;
- лимиты числа процессов/потоков, размера вывода, дискового квотирования;
- сеть отключена по умолчанию (отдельный network namespace);
- **meta-файл** с машинночитаемым результатом прогона: затраченное время, wall-время,
  max-RSS, потребление по cgroup, код возврата, статус (аварийное завершение / сигнал /
  таймаут) — это ровно то, из чего движок судейства (#163) собирает вердикт
  RE / TLE / MLE.

**nsjail** (Google) — универсальная песочница для сервисов и CTF. Для judging минусы:

- Ограничение памяти обычно через `RLIMIT_AS` (адресное пространство). Это **нечестный
  MLE**: Python и JVM резервируют много виртуальной памяти, не касаясь её, — решение
  получит MLE, реально не превысив лимит. Честный лимит всё равно требует cgroups.
- Нет готовой модели «CPU-время vs wall-время» и meta-отчёта под вердикты — учёт времени
  и классификацию исходов пришлось бы писать самим.

Наш проектный принцип — «некорректные решения должны ЧЕСТНО получать свой вердикт»
(CLAUDE.md). Инструмент, который врёт про MLE, этому принципу противоречит. Поэтому isolate.

**Цена решения:** isolate жёстче по требованиям к хосту (cgroup v2 + привилегии), и это
основной риск спайка — он и проверяется скриптом-пробой.

## 3. Требования к хосту

| Требование | Значение | Почему |
|---|---|---|
| Ядро Linux | **>= 5.10** | зрелый cgroup v2, корректный учёт памяти |
| cgroup | **v2 unified** (`cgroup2fs`) | актуальный isolate работает с cgroup v2; на v1/hybrid не заведётся |
| Контроллеры cgroup | `memory`, `pids`, `cpu`, `cpuset` | лимиты памяти, числа процессов, привязка CPU |
| Привилегии | root внутри judge-контейнера + `CAP_SYS_ADMIN` | создание namespaces и управление cgroup-деревом |
| Доступ к `/sys/fs/cgroup` | на запись из judge-контейнера | isolate создаёт вложенные cgroup на каждый прогон |
| Swap | **выключен** | со swap'ом TLE/MLE становятся недостоверными |
| CPU governor | `performance` | воспроизводимые тайминги, иначе TL «плавает» |
| Компиляторы | `g++`, `python3` | языки из #159 (YCA-402) |

Отдельно: судейский хост не должен быть перегружен посторонней нагрузкой — иначе
wall-time лимиты дают ложные TLE. На одной VM с backend/frontend это нужно учитывать
(ограничение параллельных прогонов настраивается в #160/#163).

## 4. Как проверить хост

```bash
./scripts/judge/host-probe.sh          # человекочитаемый отчёт
./scripts/judge/host-probe.sh --json   # машинный вывод
```

Скрипт read-only, ничего не меняет. Возвращает `1`, если найдено блокирующее
несоответствие. Ключевые проверки и ожидаемый результат:

| Проверка | Команда | Ожидание |
|---|---|---|
| cgroup v2 | `stat -fc %T /sys/fs/cgroup` | `cgroup2fs` (а не `tmpfs`) |
| контроллеры | `cat /sys/fs/cgroup/cgroup.controllers` | есть `memory`, `pids`, `cpu` |
| ядро | `uname -r` | >= 5.10 |
| swap | `awk '/^SwapTotal:/ {print $2}' /proc/meminfo` | `0` |
| docker на v2 | `docker info --format '{{.CgroupVersion}}'` | `2` |

Скрипт нужно запускать **дважды**: на самом хосте и (позже) внутри judge-контейнера —
внутри контейнера картина другая, и важна именно она.

## 5. Как это ложится на docker compose

Judge — отдельный сервис. Привилегии выдаются только ему: backend и frontend остаются
как есть. Ориентировочная форма (конкретика — в #158):

- отдельный образ с `isolate`, `g++`, `python3` и `testlib.h`;
- повышенные привилегии для контейнера judge (`privileged` либо точечный набор
  capabilities — что именно достаточно, определяется экспериментом в #158);
- доступ к cgroup-дереву на запись;
- отдельный volume под box-директории прогонов.

Это прямо соответствует требованию «judge = отдельный микросервис»: радиус поражения при
компрометации песочницы ограничен judge-контейнером и не затрагивает backend с кредами
платформ (которые, к слову, сейчас лежат в БД открытым текстом — см. #132/#133).

## 6. Что ещё требуется подтвердить на живом хосте

Ниже — **непроверенное**: в песочнице разработки нет ни прод-VM, ни docker, ни
установленного isolate. Это надо закрыть до старта #158.

1. **cgroup v2 на прод-VM.** Прогнать `host-probe.sh` на боевой машине.
   Машина разработки, где писался спайк, — cgroup **v1** и ядро **5.4**, то есть под
   isolate не годится; это ничего не говорит о проде, но показывает, что проверять надо.
2. **Достаточный набор привилегий контейнера.** Проверить, хватает ли точечных
   capabilities или нужен `privileged`. Определяется экспериментально в #158.
3. **Точные требования установки isolate** (пакет/сборка из исходников, версия,
   нужен ли его systemd-юнит для управления cgroup-деревом, как он ведёт себя внутри
   контейнера без systemd) — уточняется по официальному README/man при реализации #158.
4. **Отсутствие лишней нагрузки** на судейском хосте и решение, судим ли мы на той же
   VM, где крутится прод, или выносим judge на отдельную машину.

Пункты 1 и 2 — это дословно acceptance-критерий #157 («подтверждён cgroup v2 +
привилегии в проде»), и закрыть их можно только на реальном хосте.

## 7. Риски

| Риск | Влияние | Что делаем |
|---|---|---|
| На проде cgroup v1 / старое ядро | isolate не заведётся, #158 блокируется | обновление хоста, либо отдельная VM под judge |
| Требуется `privileged` для judge | шире attack surface | контейнер изолирован от backend; аудит в #169 |
| Судейство на общей с прод VM | ложные TLE из-за соседней нагрузки | ограничить параллелизм, в перспективе — отдельный хост |
| Тайминги «плавают» | нечестные вердикты | `performance` governor, swap off, extra-time isolate |
