# YCA-412 (#169): аудит безопасности песочницы

Отчёт по проверке изоляции. Проверялось не рассуждением, а прогоном настоящих атак
против настоящей песочницы — CI-джоб `judge-e2e`, скрипт `scripts/judge/run-security.py`,
исходники атак в `backend/judge/security/attacks/`.

Статус: **песочница держит удар**, судейство можно пускать в прод при соблюдении
условий из раздела 5.

## 2. Главная находка: `--processes` не является границей безопасности

isolate реализует лимит процессов через **`RLIMIT_NPROC`**, а не через cgroup-контроллер
`pids` ([isolate.c:808](https://github.com/ioi/isolate/blob/v2.6/isolate.c#L808)):

```c
if (max_processes)
  RLIM(NPROC, max_processes);
```

`RLIMIT_NPROC` не применяется к процессу, обладающему `CAP_SYS_RESOURCE`. Box работает
root'ом внутри собственного user namespace и такой возможностью там обладает, поэтому
**форк-бомба реально порождает процессы**, несмотря на `--processes=1`.

Остановила её не она, а лимит памяти: дерево процессов упёрлось в `memory.max` cgroup,
и ядро прибило его OOM-киллером. Отсюда вердикт **MLE**, а не ожидавшийся тикетом RE/TLE.

**Вывод:** containment сработал, но не тем механизмом, на который рассчитывал тикет.
Полагаться на `--processes` как на защиту нельзя — это подсказка планировщику, не барьер.

### Что сделано

В `backend/judge/entrypoint.sh` выставляется потолок на всё поддерево боксов:

```sh
echo "${JUDGE_MAX_PIDS:-1024}" > /sys/fs/cgroup/isolate/pids.max
```

Это настоящий барьер на уровне ядра: сколько бы box ни форкался, PID'ы хоста он не
исчерпает.

### Что осталось несовершенным

Потолок **общий на все боксы**, а не по одному на каждый. Значит одна форк-бомба может
съесть лимит и помешать соседним прогонам (взаимный DoS между участниками), хотя хост при
этом в порядке. Честный per-box лимит требует, чтобы isolate писал `pids.max` в cgroup
каждого box — этого он не делает. Варианты на будущее: патч в isolate, либо обёртка,
проставляющая `pids.max` в `box-N` после `--init`. Заведено как известное ограничение,
не блокирует прод.

## 3. Почему вердикт MLE у бомбы — это нормально

Набор атак принимает для бомб `RE`/`TLE`/`MLE`: любой из них означает, что решение
остановлено, а хост цел. Ужесточать до одного конкретного вердикта нельзя — какой именно
лимит сработает первым, зависит от того, сколько памяти успеет занять дерево процессов, и
это не свойство безопасности.

---

## 4. Что осознанно НЕ проверялось

- **Уязвимости самого ядра** (побег через баг в namespaces/seccomp). Вне нашей власти;
  снижается обновлением ядра хоста.
- **Побег из Docker-контейнера.** Контейнер judge работает `privileged`, поэтому побег из
  песочницы isolate в контейнер означал бы и компрометацию хоста. Именно поэтому judge —
  отдельный контейнер: у него нет ни БД, ни кредов платформ.
- **Атаки по времени/сторонним каналам** между боксами.
- **Исчерпание диска** внутри box — ограничено `--fsize`, отдельной атаки нет.

## 5. Условия допуска в прод

1. Хост с cgroup v2 и ядром ≥ 5.10 (проверять `scripts/judge/host-probe.sh`).
2. Judge — **отдельный контейнер**, без доступа к БД и кредам платформ. Привилегии только
   у него.
3. Джоб `judge-e2e` зелёный: набор атак — обязательный гейт, а не разовая проверка.
4. Судейский хост по возможности отдельный от прод-БД: `privileged`-контейнер, исполняющий
   код студентов, рядом с боевыми данными — лишний риск (см. `docs/judge/host-requirements.md`).
5. При обновлении isolate — перепроверить п.2: если появится нормальный per-box `pids.max`,
   обёртку можно упростить.

## 6. Как перепроверить

```bash
docker compose -f docker-compose.dev.yml up -d --build judge
./scripts/judge/run-security.py     # атаки
./scripts/judge/run-oracle.py       # честность вердиктов
```

Обе проверки гоняются автоматически в CI на каждом PR, трогающем `backend/judge/**`.
